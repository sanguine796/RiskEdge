Loan Risk Prediction Project Summary
====================================

1) Project Overview
1. Explain the project from start to finish
- A user registers and logs in through the web app.
- The user goes to either the default-risk form or the approval form.
- The browser validates the inputs locally.
- The frontend sends the collected data to the backend using JSON over REST.
- The backend loads the trained model from disk, converts the input into the expected feature format, runs prediction, applies business-rule overrides, and stores the result.
- The system returns the prediction and explanation back to the UI.
- The app stores the prediction history in the database and shows analytics on the dashboard and history pages.

2. Main objective
- The main objective is to help lenders quickly estimate loan default risk and make more informed approval decisions using machine learning.

3. Problem it solves
- It solves the problem of manual, inconsistent, and slow credit review by automating risk scoring and flagging borrowers who are likely to default.

4. Target users
- Loan officers
- Bank or lending staff
- Admins managing the system
- Registered users who want to evaluate applicants

5. Complete workflow
1. User logs in.
2. User enters borrower/applicant details in a form.
3. Frontend validates fields.
4. Form is submitted to /api/predict or /api/predict_approval.
5. Backend loads the relevant model from model/model.joblib or model/approval_model.joblib.
6. Features are encoded and normalized to the model's expected schema.
7. Model predicts probability.
8. Rule-based adjustments improve realism for extreme-risk profiles.
9. Result, score, and explanations are returned.
10. Prediction is stored in MySQL.
11. Dashboard/history pages show analytics, summaries, and export options.

2) Dataset
1. Which dataset is used?
- The visible training dataset in the repository is model/loan_approval_data.csv, generated by train_model.py.
- The default-risk endpoint uses a pre-trained model artifact in model/model.joblib, with feature names listed in model/features.txt.

2. Where did the dataset come from?
- It appears to be a synthetic dataset generated locally by the project itself using the logic in train_model.py.
- It is not shown as an imported external public CSV.

3. How many records and features are present?
- The visible approval dataset in model/loan_approval_data.csv has 8,000 records and 11 columns.
- The columns include 9 feature columns, 1 target column (approved), and 1 derived label column (decision).

4. Explain every feature used in the dataset
- age: applicant age
- monthly_income: monthly income
- employment_status: employment category
- years_of_employment: years in current employment
- credit_score: credit score
- existing_loan_amount: total current outstanding loans
- loan_amount_requested: requested loan amount
- loan_tenure_months: loan tenure in months
- purpose_of_loan: purpose for the loan

For the default-risk model, the feature list in model/features.txt is:
- age
- income
- employment_status
- credit_score
- loan_amount
- loan_tenure
- debt_ratio
- previous_defaults
- existing_loans

5. Which feature is the target variable?
- Approval model target: approved
- 1 = Approved
- 0 = Rejected

- Default-risk model target is the probability of default, shown as Default vs Non-Default.

6. Why were these features selected?
- They are the core financial and applicant profile signals lenders usually use to judge repayment ability and creditworthiness.

7. Were any features removed? Why?
- The derived label column decision is not used as a model feature.
- The target variable approved is separated from the feature matrix during training.
- No other visible feature removal is coded in the training pipeline.

3) Data Preprocessing
1. How is missing data handled?
- The generated dataset is synthetic and does not show missing values by default.
- At prediction time, the backend replaces invalid numeric input with 0.0 or a fallback default in app.py.
- Category fields fallback to a default mapping if the value is unknown.

2. How are categorical variables encoded?
- employment_status is mapped to numeric values:
  - salaried / employed -> 1.0
  - self-employed -> 2.0
  - unemployed -> 0.0
  - student -> 0.5
- purpose_of_loan is mapped to numeric indices in train_model.py.

3. Is feature scaling applied? Why?
- No explicit scaling like StandardScaler is used.
- This is appropriate because the main model is a tree-based ensemble, which does not require feature scaling.

4. How were outliers handled?
- The synthetic generator clips values to realistic bounds in train_model.py.
- Extreme-risk rule overrides in app.py also catch outlier-like patterns such as very low income, low credit score, or very high debt.

5. How was the data cleaned before training?
- Data was generated with bounded realistic ranges.
- Categorical variables were mapped to numeric codes.
- The dataset was balanced by employment and income bins.
- Then it was split using stratified train/test sampling.

4) Machine Learning
1. Which machine learning algorithm is used?
- Default-risk model: RandomForestClassifier
- Approval model: CalibratedClassifierCV wrapping a RandomForestClassifier

2. Why was this algorithm selected?
- Random forests are robust on mixed numeric and categorical tabular data.
- They handle nonlinear patterns well.
- They provide feature importance for explanations.
- Calibration improves probability reliability.

3. Which other algorithms were considered?
- No alternate algorithms are explicitly implemented in the visible codebase.
- The visible pipeline uses Random Forest and calibration.

4. What are the hyperparameters used?
- Approval model:
  - RandomForestClassifier(n_estimators=150, random_state=42)
  - CalibratedClassifierCV(method='isotonic', cv=5)

- Default model artifact:
  - Verified model type is RandomForestClassifier
  - It uses the default sklearn settings from the saved artifact, including n_estimators=100

5. How is the model trained?
- Generate synthetic data
- Add income bins
- Balance groups by employment and income bin
- Map categorical fields
- Split into train/test with stratification
- Fit RandomForestClassifier
- Calibrate probabilities with CalibratedClassifierCV
- Save the model and feature list

6. How is overfitting prevented?
- Stratified train/test split
- Balanced sampling to reduce bias
- Ensemble model structure
- Probability calibration
- No visible use of a very deep tree configuration

5) Model Evaluation
1. What evaluation metrics are used?
- Accuracy
- Precision
- Recall
- F1-score
- Confusion matrix

2. What is the accuracy of the model?
- The approval model was verified on the shipped synthetic data with an accuracy of 0.965375, which is 96.54%.

3. What are the precision, recall, and F1-score?
- Precision: 0.9630
- Recall: 0.9822
- F1-score: 0.9725

4. What does the confusion matrix indicate?
- Confusion matrix: [[2824, 188], [89, 4899]]
- 2824 true rejections
- 188 false approvals
- 89 false rejections
- 4899 true approvals

5. Why is accuracy alone not enough?
- Accuracy alone can hide the cost of false positives and false negatives.
- In lending, approving a risky borrower can cause losses, while rejecting a good borrower can lose business.
- Precision and recall are important because they show how often the model is right on risky and safe cases.

6) Prediction
1. How does the system predict loan risk?
- The default-risk API in app.py receives the form fields, encodes them, builds a feature vector, runs predict_proba, then applies override rules and stores the result.

2. What factors influence the prediction the most?
- The main influential signals are credit score, income, debt ratio, loan amount, existing loans, and previous defaults.

3. How is the prediction displayed to the user?
- The frontend displays prediction label, risk category, risk score, probability, and key factors.

4. Does the model explain why a prediction was made?
- Yes. The backend returns a reasons list based on feature importance and override factors.
- The API /api/prediction/<id>/explain provides more detailed reasoning.

7) Frontend
1. Which frontend technologies are used?
- HTML templates with Jinja2
- Bootstrap 5
- Custom CSS
- Vanilla JavaScript
- Chart.js

2. Explain every page in the application
- templates/index.html: landing page and project overview
- templates/register.html: signup page
- templates/login.html: login page
- templates/dashboard.html: analytics dashboard
- templates/predict.html: default-risk prediction form
- templates/predict_approval.html: approval prediction form
- templates/history.html: past prediction history
- templates/admin.html: admin operations

3. How does the user interact with the system?
- Users log in, fill out forms, submit them, and view results.
- The dashboard and history pages let them review analytics and stored predictions.

4. How is form validation implemented?
- HTML fields use required, min, max, and numeric constraints.
- On submit, the JS checks form.checkValidity().
- If invalid, the form shows Bootstrap validation styling through was-validated.

8) Backend
1. Which backend framework is used?
- Flask with Flask-SQLAlchemy.

2. Explain the folder structure of the backend
- app.py: app factory, routes, prediction logic, API endpoints
- models.py: database schemas
- train_model.py: data generation and training
- model/: stored models and feature lists
- templates/: frontend HTML
- static/: CSS and JS assets
- instance/: local app data
- test files: API and prediction tests

3. How does the frontend communicate with the backend?
- The frontend uses fetch() to POST to /api/predict, /api/predict_approval, /api/history, and /api/dashboard_data.
- The session cookie manages login state.

4. Explain the prediction API step by step
- Receive JSON payload from the frontend
- Load model from model/model.joblib
- Read expected feature names from model/features.txt
- Encode employment_status
- Convert values to floats with fallback defaults
- Build a DataFrame
- Call predict_proba
- Apply risk-rule overrides
- Determine label and category
- Save the prediction to the database
- Return JSON with probability, score, reasons, and prediction ID

5. How is the trained model loaded?
- The app uses joblib.load() for the model file.
- Feature names are loaded from a text file.
- The model is cached in app.ml_model and app.approval_model.

9) Database
1. Which database is used?
- MySQL is the configured database.

2. What tables are present?
- user
- prediction
- approval_prediction

3. Why did you choose this database?
- MySQL is a reliable relational database for production-style web apps, and it integrates well with SQLAlchemy for user management, audit history, and analytics.

4. How is user data stored?
- User stores email, name, password_hash, and is_admin.
- Passwords are hashed with Werkzeug.
- Prediction stores default-risk predictions and feature snapshots.
- ApprovalPrediction stores approval predictions and scores.
- Timestamps are stored with created_at.
